## AD-01 brain/body 职责边界：业务下沉 body，Termux 只承载 pi 核心 Loop

- **状态**：已决（2026-08-19 修订 pi 生态范围，原"承载 pi 原生生态"过宽，见 AD-05）
- **日期**：2026-08-18
- **背景**：
  docs/05 §2.2 原设计"第1层 brain 守卫持有提交边界词表"导致 brain 与 body 双侧维护同一份词表（`commitBoundary.ts` ↔ `Guard.kt`），出现"同源治理"症状——本质是职责错位。

- **决策**：
  1. **Termux 侧只承载 pi 核心 Loop**：仅用 `pi-agent-core` 的 `Agent`（工具循环 + steering/follow-up/abort 语义）+ `pi-ai`（Provider 解耦 + GLM 接入）。**不用** `AgentHarness`/`Session`/`JsonlSessionRepo`/`loadSkills`（见 AD-05）。
  2. **业务逻辑、安全闸门、硬件交互一律下沉 body（Kotlin/Java/C++）**：提交边界词表、敏感 App 注册表、敏感会话追踪、技能存储与检索、声纹库、脱敏——单一主源在 body，brain 只读 body 下发的标记字段（`sensitive`/`sensitiveSession`/`appPackage`），不持有任何业务词表。
  3. **Kotlin = UI**，**Java/C++ = 后台服务/native 实现**。Termux 不扩散到业务，仅保 pi 核心 Loop 兼容性。
  4. **brain 守卫层瘦身**：`beforeToolCall` 只做"读 body 下发标记 + 证据闸门"，不做业务判定；`afterToolCall` 只做 trace 追踪与状态镜像，不重算敏感态。

- **理由**：
  - 安全权威必须单点：body 是"做"的最高权威，brain 幻觉/被注入绕不过 body 硬红线。若 brain 也持有词表做判定，就出现"两个权威"——同源治理是补丁，治本是只留一个。
  - 移动脚手架归位：TF-IDF 检索、技能状态机、声纹嵌入存储本就是设备端业务/数据，天然属于 body。

- **影响**：触发 R1（已完成）/R2/R3 重构（见下，范围经 AD-05 修订）。

## AD-05 pi 用法边界与周边重实现参照（取代 AD-03/04）

- **状态**：已决
- **日期**：2026-08-19
- **背景**：
  调研 pi 官方仓库 + 三个本地参考项目（agentos-android/android-agent/clowder-ai）后发现：
  1. pi 的 AgentHarness/Session/JsonlSessionRepo/compaction/lane 是 **coding-agent CLI 场景**的会话管理，经 agentos-android 研究文档论证不适合系统级 Agent（durability/完整性/权威状态分离均不足）。
  2. 三个参考项目无一使用 pi AgentHarness；均自研会话/任务/证据/技能机制。
  3. Kestrel（android-agent）已实现成熟的 Android Agent 周边能力：RunTraceBuilder（失败可见性留痕）、ReActGuard（卡死/振荡/无进展/绕圈止损）、FinishEvidence（防幻觉新颖性闸门）、SkillLearner/SkillReplayer/SkillStore（技能飞轮）、HumanInTheLoop（支付红线硬停手）。
  4. agentos-android 的 `ActionCommitAuthority`（持久线性化 + FinalGate + 阶段机 + 幂等）是提交权威内核的硬核参考。

- **决策**：
  1. **pi 只用核心 Loop**：`Agent`（工具循环 + steering/follow-up/abort）+ `pi-ai`（Provider 解耦）。周边（Session/AgentHarness/JsonlSessionRepo/loadSkills/compaction）**不用**。
  2. **会话持久化与断点续跑**：本项目自实现，保留 `runState.ts` 并按 Kestrel `RunTraceBuilder` 重做——失败可见性留痕（成功/失败/崩溃都落全历史）、trace 单调序号、脱敏后落盘。断点续跑 = 恢复后从最后 trace 步骤重新感知当前屏幕，diff 后决定续走或重规划。
  3. **证据闸门**：保留 `guards/finish.ts`，按 Kestrel `FinishEvidence` 增强——新颖性核验（证据须在任务起点帧之后新出现，防旧状态冒充新成果）。
  4. **ReAct 止损**：新增 `guards/reactGuard.ts`，参照 Kestrel `ReActGuard`——MaxSteps 硬顶、NoProgress（连续 K 次页面签名不变）、Oscillation（ABAB）、Looping（坐标桶绕圈）、Revisiting（屏幕签名重访）。brain 侧 beforeToolCall 查询 guard，触发则强制 finish(false) 或 NeedsHuman。
  5. **技能飞轮**：本项目自实现，参照 Kestrel `core-skill`——learn（trace→SkillLearner）/replay（SkillReplayer 零模型回放 + sensitive 步停手交接）/curator（consecutiveFailures 降级）/search（2-gram TF-IDF）。检索下沉 body `skill.search` RPC（Kotlin 实现）；学习/回放保持 body `skill.learn`/`skill.run` RPC。删 brain `skills/index.ts`。
  6. **提交权威**：body 侧 `Guard.kt` 当前词表匹配为 v2；远期参照 agentos-android `ActionCommitAuthority` 升级为持久线性化 + FinalGate + 阶段机（P2）。

- **理由**：
  - pi 核心 Loop 优秀（§4.1：小而清晰的 Loop + Provider 解耦 + steering/follow-up/abort 语义），值得复用。
  - pi 周边（Session/compaction/loadSkills）是为 coding-agent CLI 设计，durability/完整性不足系统级 Agent 要求；本项目周边需求（断点续跑/证据闸门/止损/技能飞轮）有更强的确定性/可审计性要求，自实现更稳。
  - Kestrel 已用真机实证打磨出成熟不变量（动作后重感知、finish 新颖性、false finish 止损、支付红线硬停手、技能 sensitive 步交接），直接参照避免重走弯路。

- **影响**：R2/R3 范围修订（见下表）。

## AD-07 brain↔body 通信通道：HTTP RPC over 0.0.0.0

- **状态**：已决
- **日期**：2026-08-19
- **背景**：真机验证发现 Android loopback `127.0.0.1` 是 per-uid 网络命名空间隔离的——body 进程的 127.0.0.1 与 Termux 进程的 127.0.0.1 不互通，Termux 连 ECONNREFUSED。
- **决策**：body NanoHTTPD bind `0.0.0.0`（所有接口）使 Termux 进程可达。随机 token 鉴权保护；P0 内部版可接受局域网暴露；P1 收紧（Unix domain socket 或 localhost + adb forward 替代）。
- **验证**：Termux node 进程经 `127.0.0.1:8765` 成功调 body `/health`（200 OK）、`perceive.screen`（15 节点）、`control.tap`（located=true）。完整链路：Termux(pi-agent brain) → HTTP RPC → body(Kotlin service) → a11y 感知/操控。
- **影响**：BodyContext 默认 host 改 `0.0.0.0`；docs/05 通知文案更新。

## AD-08 brain 打包与部署：esbuild ESM bundle，pi 生态 external

- **状态**：已决
- **日期**：2026-08-19
- **背景**：
  1. 首次打包 `brain.cjs`（CJS 全 bundle，1.6MB）部署 Termux 后，`resolveModel` 报 `TypeError: ModelsImpl is not a constructor`——esbuild 打包 `pi-ai`（纯 ESM）成 CJS 时破坏了类初始化时序/作用域。
  2. `node -e "require('@earendil-works/pi-ai')"` 报 `ERR_PACKAGE_PATH_NOT_EXPORTED`（pi-ai 无 CJS main，仅 ESM exports）。
  3. 结论：**不打包 pi 生态**，改为 external + Termux 侧 npm 预装（纯 JS，arm64 兼容已验证）。
- **决策**：
  1. **打包**：`build.mjs` 用 esbuild API（非 CLI，避免 PowerShell 引号吞 banner）——`format=esm`、`external: ["node:*", "@earendil-works/*", "typebox"]`、banner 注入 `createRequire` polyfill（兼容依赖里的动态 require）。产物 `dist/brain.mjs` 约 45KB，仅含本项目代码。
  2. **部署**：brain.mjs 必须放在装有 node_modules 的目录（Termux `~/brain-lite/`），pi 依赖从该目录解析；传输用 `adb push /data/local/tmp` + `run-as com.termux cp`（adb 命令行长度限制，base64 直传不可靠）。
  3. **运行**：环境变量 `GLM_API_KEY`/`BODY_URL`/`BODY_TOKEN`；Termux 内 `input text` 不支持中文注入（用英文任务或文件重定向），`~` 不展开（用绝对路径）。
  4. **开发机直连**：`adb forward tcp:8765 tcp:8765` 后 PC 上跑 brain.mjs 即可操控真机 body，输出直接可读（用于调试/验收）。
- **理由**：pi 生态依赖固定且成熟，bundle 它们引入打包器语义风险（ESM/CJS 互操作、类身份破坏）得不偿失；Termux 预装依赖是低成本且已实证的方案。
- **影响**：`build.mjs` 加入仓库；`dist/` gitignore 不入库；Termux `~/brain-lite/node_modules` 为运行前置条件。

- **HITL 沉默≠授权**：60s 超时=拒绝，与 agentos HITL-011"沉默不构成授权"一致。

### 择期采纳（进 docs/10 计划）

- **重模型 worker 隔离进程**：agentos AD-002 PC-3/ADR-003 明确"模型/ASR/TTS worker 独立进程、无通用权限"——为 G3.1 的 `:tts` 隔离进程二级方案提供设计背书（若 noCompress 复测仍被杀）。

### 明确不采纳（P0，防过度工程）

- **ActionCommitAuthority 全套**（prepare/commit 两阶段 + 8 引用权威向量）：为 ROM 级 OS 设计；我们单用户 P0 原型的风险面已由"幂等键 + COMMIT_BOUNDARY 硬拦 + 敏感会话 action 放行"覆盖。其"denial is data / retry 是新 attempt / unknown 禁盲重试"三条语义已作为原则吸收进错误码与重试设计。远期（P2 多设备/EV 轨道）再评估移植其纯 Java 实现（ActionCommitAuthority.java，Java 17 无 Android 依赖，可移植性好）。

## AD-10 HITL 确认协议 v2：动作绑定 nonce（立项设计，2026-08-19，源自 GPT 5.6 审计 P0-05）

- **状态**：已设计待实施（A2）
- **背景**：现协议中模型自拟确认文案与 action 参数，body 无法核实"用户批准的就是即将执行的动作"；批准虽有单次消费（e5abf49）但未绑定原始拒绝上下文。
- **设计**：
  1. body 侧拒绝敏感动作时生成 **nonce**：`HMAC(bootSecret, 前台包名|动作标签|参数摘要|时间窗)`，随 COMMIT_BOUNDARY(sensitive_session) 错误返回 `nonce` 字段。
  2. `hitl.confirm` 必须携带该 nonce；body 校验（前台包名未变 + 标签一致 + 时间窗 ≤120s）后才向用户呈现**服务端规范化文案**（"即将在 微信 执行「发送」，确认？"），拒绝模型自拟文案承载授权语义。
  3. 用户批准 → nonce 原子消费（一次性）；同 nonce 重放=duplicate，不同语义=integrity conflict（对齐 agentos HITL-026）。
  4. 契约变更：错误响应加 `nonce?`；hitl.confirm 参数改 `{nonce}`（prompt 字段降级为展示辅助）。
- **验收**：真机三类用例（支付/发送/删除）各验：批准放行一次、拒绝不放行、重放拒绝。

## AD-11 动作执行统一收口：ActionExecutor（立项设计，2026-08-19，源自审计 P0-04）

- **状态**：已设计待实施（A1，设备空窗期执行）
- **背景**：RPC 处理器、OptionSelector、SkillStore.executeStep 三路各自拼装 闸门/执行/签名 逻辑，审计指出回放路径弱于 RPC 路径（现以 ActionGate 过渡收窄差距）。
- **设计**：
