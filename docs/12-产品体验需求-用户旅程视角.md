# 12 · 产品体验需求与 Kestrel 交互复用审计

> 状态：UX 行为基线 v2.1（UI-0 冻结；UI-1 语音部分为 v3 预研草案），2026-08-19
>
> 决策来源：用户旅程定义、用户确认的方案 A，以及对 `D:\vibecoding\android-agent`（Kestrel）实际代码、布局、测试和真机记录的复核。
>
> 本文定义用户可观察行为与验收标准。架构拆分、协议落盘和实现排期由实现负责人基于本文继续设计。

## 1. 产品目标

用户不接电脑即可完成完整闭环：

1. 打开应用，或从常驻入口呼出助手；
2. 使用文字输入指令，语音输入在下一阶段接入；
3. 助手确认收到，理解意图并规划；
4. 助手操作目标应用；
5. 屏幕始终给出真实、简短的当前状态和当前一步；
6. 用户可随时查看最近步骤、暂停或停止；
7. 完成、失败、需要确认或需要接管时给出明确反馈。

默认界面采用用户确认的方案 A：**只显示“当前状态 + 当前一步”**。历史步骤和控制项按需展开，不持续占据屏幕。

## 2. 当前现状与核心缺口

| 用户环节 | 当前 SuperAgent 状态 | UX 判定 |
|---|---|---|
| 首次打开与授权 | `MainActivity` 是开发者装配页；权限入口存在但没有产品化引导 | 可复用底层，需重做用户流程 |
| 后台运行 | FGS 和无障碍服务存在；`START_STICKY` 在华为设备上不能保证恢复 | 部分可用，不能承诺绝对常驻 |
| 文字输入 | 只有 PC REPL/调试入口 | 产品不可用 |
| 理解与规划 | pi-agent-core + GLM 主链已验证 | 复用 |
| 执行动作 | body 操控、守卫、HITL 和技能回放已存在 | 复用，继续按安全审计修复 |
| 当前状态 | EventBus 和部分运行状态存在，没有产品 UI | 数据基础可用，展示缺失 |
| 最近步骤 | trace/event 可提供数据，没有用户入口 | 缺失 |
| 完成反馈 | 主要在 REPL；TTS 尚不稳定 | UI-0 先做文字反馈 |

结论：当前主要缺口不是“大脑不会执行”，而是用户没有可靠的输入、控制和反馈表面。

## 3. Kestrel 审计结论

### 3.1 已由真机证明、复用其用户行为或设计模式

本节的“复用”不等于复制 Kestrel 源码或协议。UI 表面与权限流程可复用用户行为；状态控制只复用“事件 -> 有限状态 -> UI”的单向映射模式。SuperAgent 的状态枚举、任务生命周期和跨进程事件均按 pi-agent-core 重新设计。

| Kestrel 能力 | 复用结论 | 对应体验 |
|---|---|---|
| 首启检查无障碍与悬浮窗，缺哪项就直达对应系统设置 | 复用行为和文案原则 | 不让用户点“启动”后静默失败 |
| `TYPE_APPLICATION_OVERLAY` 侧边悬浮球 | 复用 | 常驻入口小、可拖动、不挂无意义角标 |
| 点击悬浮球先展开待命面板 | 复用 | 避免一次点击直接误提交或误录音 |
| 文字输入使用独立半透明 `CommandInputActivity` | 复用 | 只有打字时获取键盘焦点，执行 HUD 永不抢焦点 |
| `AgentStateController` 将运行事件转换为有限 UI 状态 | 仅复用模式，不复用类/枚举/事件 | UI 不读取内部实现细节，不展示模型原始输出 |
| 当前动作优先显示控件语义，如“正在点击「发布」” | 复用 | 不向用户展示坐标、工具名或 JSON |
| ReAct 总步数未知时只显示步骤序号 | 复用 | 禁止伪造百分比和完成时间 |
| 长日志放 Detail 页，不塞进悬浮窗 | 复用 | 默认只显示当前一步 |
| 敏感操作、验证码和故障使用独立状态 | 复用 | 用户能区分“需要批准”“需要接管”“执行失败” |
| 关闭敏感确认等价拒绝，不得等价批准 | 复用为安全红线 | 返回键、关闭按钮和超时都不能误授权 |
| 无悬浮窗能力时用高优先级通知兜底 | 复用 | 用户仍可停止或处理 HITL |
| 截图前通过 `OverlayGate` 隐藏 HUD，截图后恢复 | 复用 | UI 不污染视觉感知，也不遮住模型要找的控件 |
| FGS `START_STICKY` + OEM 后台设置提示 | 复用但如实降级 | 不把系统可能阻止的恢复宣传成“永不掉线” |

主要参考实现：Kestrel `AgentService.kt`、`CommandInputActivity.kt`、`AgentStateController.kt`、`FloatingPanels.kt`、`OverlayGate.kt`、`docs/run-on-device.md` 和 `docs/ui/ui-design-spec.md`。

### 3.2 Kestrel 不好用之处，本项目改进

| Kestrel 现状 | 问题 | SuperAgent 改进 |
|---|---|---|
| 执行态用全宽、不可触摸的状态条替换悬浮球 | 状态条无法点击；暂停/停止主要依赖通知栏 | 执行态保留两个独立表面：不可触摸的状态条 + 可触摸的侧边控制球 |
| 待命球点击只展开待命面板，进入执行态后又被状态条替换 | 运行中没有可直接触达的详情和控制入口 | 运行时保留控制球；点击后先请求安全暂停，再打开最近步骤和控制面板 |
| 运行面板布局仍包含较多视觉元素 | 长任务持续遮挡面积偏大 | 默认压缩为单行“状态 + 当前一步”，不显示装饰性进度条 |
| 细节只能进入主应用 Detail 页 | 查看详情会明显离开当前上下文 | 先提供轻量最近步骤面板；完整日志仍进入主应用 Detail 页 |
| 本地编排进度直接驱动 UI | 不适用于 Termux 中的 pi-agent-core | 保留 UI 状态机，替换事件来源；brain 只提供经过整理的状态事件 |

### 3.3 明确不复用

- 不复用 Kestrel 自研 Orchestrator、Planner、云模型配置和技能编排核心；大脑仍是 pi-agent-core。
- 不把 Kestrel 的 `OrchestratorProgress` 当跨进程协议；它只作为 UI 状态设计参考。
- `BrainEvent` 是 SuperAgent 针对跨进程重新设计的协议：以 `taskId` 隔离任务、以 `seq` 排序去重、以有限枚举封闭语义；它不是 `OrchestratorProgress` 的改名或序列化版本。
- 不复制 Kestrel `AgentStateController` 的代码和迁移表；仅复用“事件输入 -> 单一有限状态 -> UI 渲染”的模式，实际状态机必须服从 pi run 与 body action gate 的生命周期。
- 不把悬浮窗作为敏感操作的最终授权权威。SuperAgent 继续遵守 AD-10：批准必须绑定 body 生成的一次性 nonce，并由可信确认表面呈现。
- UI-0 不接 ASR、KWS 和持续监听。麦克风权限不是文字首版的启动前置条件。

## 4. 冻结的交互模型

### 4.1 三个表面

#### A. 侧边控制球

- 约 48 至 56dp 的稳定触摸区，可上下拖动，停靠屏幕左右边缘。
- 待命时是主要呼出入口；运行时始终保留，是唯一常驻可触摸区域。
- 不显示常驻数字。只有“需要用户处理”或“有未读结果”时显示短状态点。
- 点击行为按任务状态变化：
  - 待命：展开待命面板；
  - 运行中：请求在安全边界暂停，随后展开任务控制面板；
  - 已暂停/待确认/受阻：直接展开对应面板；
  - 已完成/失败：展开结果摘要。

#### B. 穿透状态条

- 默认只显示状态和当前一步，例如：`执行中 · 正在点击「搜索」`。
- 位于顶部安全区，宽度按内容约束，不做全屏底部遮挡。
- 始终 `FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCHABLE`；它本身不可点击。
- Android 12+ 必须验证“不可信触摸遮挡”行为；透明度需低于系统拦截阈值并留余量，Kestrel 的真机值为 `0.75`。
- 规划和执行时显示；待命时隐藏；完成/失败摘要短暂显示后收起。
- 不显示滚动日志、原始模型文本、内部工具名、坐标、JSON、思维链或伪造的百分比。

#### C. 半透明交互面板/Activity

- 待命面板提供“文字输入”和后续的“语音输入”入口。
- 文字输入使用独立半透明 Activity，而不是临时把 overlay 改为可聚焦窗口。
- 任务控制面板展示最近 3 至 5 条用户可读步骤，以及继续、停止、查看完整详情。
- 打开任务控制面板前必须先安全暂停，避免用户操作控制面板时 agent 同时点击底层应用。
- 敏感确认使用 body 权威生成的文案和 nonce；普通状态面板不得伪装成授权确认。

### 4.2 为什么不能让执行状态条直接可点

Kestrel 真机已验证两个 Android 行为：

1. 可触摸 overlay 会直接拦截目标应用对应区域；
2. Android 12 的不可信触摸保护可能丢弃“穿过较不透明 overlay”的触摸，即使窗口设置了 `FLAG_NOT_TOUCHABLE`。

因此“状态条可点展开”和“完全不挡 agent 操作”不能同时成立。冻结方案是：**状态条负责看，侧边控制球负责点**。

## 5. 端到端用户旅程

### 5.1 首次打开

1. 首页只展示当前就绪状态和下一项必须操作，不先展示开发者参数。
2. UI-0 必需项：通知、悬浮窗、无障碍、body 与 brain 连通。
3. 每项权限都说明用途，并由用户点击后跳转系统授权页面；应用不得代替用户开启权限。
4. 用户从系统设置返回后立即重新检查，已通过项自动完成。
5. UI-0 不要求麦克风权限。ASR 启用时再按需申请。
6. 全部就绪后，用户明确开启“后台运行”，出现前台服务通知和侧边控制球。
7. 若 OEM 还需“允许后台活动/自启动”，给出设备相关引导，但不得宣称应用能绕过系统限制。

### 5.2 呼出与文字输入

1. 用户点击侧边控制球，看到简洁待命面板。
2. 用户点击键盘图标，打开半透明文字输入 Activity，输入框自动聚焦并呼出键盘。
3. 取消、返回或空文本不产生任务。
4. 点击发送后，同一条指令只能入队一次；输入 Activity 关闭。
5. 300ms 内给出本地受理反馈：`已收到 · 正在理解`。这不代表 brain 已完成规划。
6. brain 不可用时直接显示 `大脑未连接` 和恢复入口，不允许无限转圈。

### 5.3 理解与规划

1. 状态条显示 `理解中` 或 `规划中`，并用一句话复述当前目标。
2. 不向用户展示思维链和内部提示词。
3. 存在关键歧义时先提问，不猜测收件人、金额、账号、目标 App 等高影响信息。
4. 无法预知总步数时不显示百分比、剩余时间或 `3/10`；只显示已发生的步骤序号。
5. 收到重复、过期或乱序事件时，UI 不倒退到旧状态。

### 5.4 执行、暂停、继续和停止

#### 5.4.1 pi-agent-core 控制边界

本项目的大脑是 Termux 中的 pi-agent-core Agent；Kestrel 的 `OrchestratorProgress` 只借鉴用户可见的步骤语义，不作为控制协议。实现必须遵守以下事实：

1. `agent.abort()` 只能中止当前 agent run/模型循环，不能撤销已经发给 body 的点击、输入、滑动或技能副作用。
2. `agent.steer()` 只在当前工具批次排空后把新消息插入下一轮；它不是暂停按钮，也不能跳过当前工具调用。
3. pi-agent-core 默认允许并行工具执行；所有会改变设备状态的工具必须在 body 侧串行化，暂停/停止以 task action gate 为最终裁决。
4. body 的执行准入闸门（execution admission gate，不是现有敏感动作 `ActionGate`）必须带 `taskId` 和动作序号；闸门关闭后，任何新动作在进入设备 API 前拒绝，不能只依赖 brain 的布尔 stop flag。
5. `skill.run` 是复合动作时，必须在每个子步骤之间再次检查闸门；不能把一个长 RPC 当作不可暂停的黑盒。
6. pi-agent-core 收到 abort signal 后，`agent.prompt()` 可能以 `stopReason=aborted` 正常 resolve，而不是进入 `catch`；brain 必须结合本次暂停/停止控制上下文和 stop reason 生成 `paused/stopped`，不能把 resolve 当成功，也不能把 abort 当普通失败。

#### 5.4.2 暂停（用户想查看或暂时接管）

1. 用户点击侧边控制球；body 先把当前任务的 action gate 原子切换为“拒绝新动作”，并立即显示 `正在暂停…`（目标：本地反馈不超过 200ms）。
2. `PAUSING` 期间不再开始新的设备动作；已经进入设备 API 的单个不可分割动作允许自然结束并记录结果。
3. body 通知 brain 中止当前 pi run；brain 需等待正在收尾的工具/事件完成，再清理本轮待执行队列。不得将 `steer()` 当作暂停确认。
4. 若在途动作结果可验证，重新感知当前前台界面并进入 `PAUSED`；若结果不可验证，进入 `BLOCKED`，文案必须是 `无法确认刚才动作是否生效，请你检查`，不得假设成功或失败。
5. 只有进入 `PAUSED`/`BLOCKED` 后才打开任务控制面板，面板展示最近 3 至 5 条已发生步骤和当前影响摘要。面板出现期间 action gate 保持关闭。
6. 暂停请求必须幂等；重复点击不能创建多个中止、恢复或任务。

#### 5.4.3 未知副作用的人工核对

1. `BLOCKED/unknown_side_effect` 面板必须显示待核对的动作摘要，不显示泛化的“继续”。暂停场景提供 `已生效，按当前界面继续`、`未生效，重新规划`、`仍无法确认，停止任务`；停止场景只允许记录核对结果或保持待检查，不允许恢复原任务。
2. 用户选择必须形成与 `taskId + actionId` 绑定的 `applied/not_applied/still_unknown` 处置事件；`still_unknown` 保持 action gate 关闭并留在 `BLOCKED`。
3. 暂停场景选择 `applied` 时跳过该动作并重新感知后继续；选择 `not_applied` 时从当前界面重新规划，不能直接重放旧调用。
4. 停止场景完成核对后进入 `STOPPED`，结果摘要注明动作已生效/未生效；无论核对结果如何都不得自动恢复任务。

#### 5.4.4 继续

1. `PAUSED` 下用户点击继续；body 先关闭面板，再保持控制球可见，并显示 `正在确认当前界面…`。
2. brain 以当前屏幕重新感知为起点规划，不重放上一个已确认成功动作；若上一个动作结果未知，必须先转人工确认或重新询问。
3. 重新建立 action gate 后才进入 `THINKING`/`RUNNING`；恢复失败进入 `BLOCKED` 或 `FAILED`，不能静默回到运行态。

#### 5.4.5 停止

1. 用户在 `THINKING`、`RUNNING`、`PAUSING`、`PAUSED` 或 `BLOCKED` 点击停止；body 立即关闭 action gate，并取消尚未发出的动作。
2. brain 调用 pi `abort()` 并等待 run settle；停止请求优先级高于暂停、继续和新指令，重复停止是幂等操作。
3. 已进入设备 API 的动作不保证可撤销：可验证无副作用才显示 `已停止`；结果未知则显示 `停止中，正在确认设备状态`，随后转 `BLOCKED`/人工接管。
4. 停止完成后不得自动继续、自动重试或重放最后一步；新任务必须由用户重新明确发送。
5. 停止事件与暂停事件必须可区分（至少 `stopped`、`paused`、`unknown_side_effect` 三种结果），不能用一个 `aborted` 值让 UI 猜测。

#### 5.4.6 动作类别和安全边界

| 动作类别 | 暂停/停止时的处理 | 用户可见结果 |
|---|---|---|
| 只读感知（截图、读取 UI） | 可让当前调用收尾；结果不得触发新动作 | 已感知/已停止 |
| 单个点击、输入、滑动、启动 App | 已入设备 API 的动作收尾；不可回滚 | 成功可验证则暂停/停止，否则未知副作用 |
| `skill.run` 复合动作 | 每个子步骤前检查 gate；关闭后不进入下一步 | 显示已完成子步骤和未执行步骤 |
| 模型流/规划 | 立即 abort；不得继续消费旧计划 | 已暂停或已停止 |
| HITL 等待 | 关闭/超时/停止均按拒绝处理；nonce 失效 | 需要用户处理/已停止 |
| ASR/TTS（UI-1） | 停止录音或播报，不产生设备动作 | 录音已取消/播报已停止 |

#### 5.4.7 竞态与断连

- 控制优先级固定为：`STOP > PAUSE > RESUME > NEW_TASK`。一旦 `STOPPING` 被接受，后到的继续、恢复和新指令全部丢弃并提示用户重新发送。
- 每次 brain 进程启动生成新的 `sourceSessionId`；事件按 `sourceSessionId + seq/eventId` 排序去重，并以 `taskId` 隔离任务。`seq` 只要求在同一 source session 内单调，合法新会话可建立新水位；旧会话事件不得恢复当前任务。
- body 与 brain 断连时 action gate 默认关闭；恢复后先感知，不得盲目重放；无法确认时进入 `BLOCKED`。
- 每次截图/视觉感知前隐藏全部 overlay；采集完成后按真实状态恢复状态条、控制球和面板，不得只恢复一个球。

### 5.5 用户确认与人工接管

| 场景 | 默认状态 | 用户动作 |
|---|---|---|
| 普通但敏感的可恢复动作 | `等待确认` | 在可信确认表面批准一次或拒绝 |
| 支付、付款、转账等红线 | `需要你接管` | agent 停手，用户亲自完成或停止任务 |
| 验证码、滑块、登录失效 | `需要你处理` | 用户处理后点继续，或停止 |
| 权限缺失 | `需要授权` | 跳转对应系统设置，返回后重新检查 |
| body/brain 断连 | `连接中断` | 自动有限重试，并提供停止与诊断入口 |

安全语义：关闭、返回、超时和通知被划走都不构成批准；一次批准只对应一个已绑定动作，并且只能消费一次。

### 5.6 完成与反馈

- 成功：显示 `已完成`、一句结果和可验证证据摘要；不得仅依据模型停止输出宣称成功。
- 失败：显示失败在哪一步、是否执行过可能产生副作用的动作，以及建议的下一步。
- 转人工：显示 agent 已停止自动操作，以及用户需要完成什么。
- 结果摘要保留数秒后收回侧边控制球；有未读结果时保留状态点。
- 完整步骤、时间、证据和错误详情进入主应用 Detail 页。
- TTS 只播报“收到、需要你处理、完成/失败”等关键节点，不逐步朗读。UI-0 不以 TTS 可用为前置条件。

## 6. 用户可见状态机

| 状态 | 默认展示 | 可用操作 | 退出条件 |
|---|---|---|---|
| `OFFLINE` | 控制球状态点 | 打开诊断、重试 | body/brain 恢复 |
| `MINI` | 仅侧边控制球 | 呼出 | 用户点击 |
| `IDLE` | 待命面板 | 文字输入、关闭 | 发送或关闭 |
| `INPUT` | 半透明输入 Activity | 发送、取消 | 发送或取消 |
| `THINKING` | 穿透状态条 + 控制球 | 点击控制球请求暂停/停止 | 产生计划、失败或取消 |
| `RUNNING` | 当前一步 + 控制球 | 点击控制球请求暂停 | 步骤完成、HITL、结束 |
| `PAUSING` | `正在暂停…` | 停止 | 到达安全边界 |
| `PAUSED` | 控制面板 | 继续、停止、详情 | 用户选择 |
| `STOPPING` | `停止中，正在确认设备状态` | 仅查看详情 | pi run settle 且在途动作结果已判定 |
| `STOPPED` | `已停止` + 已确认的影响摘要 | 收起、详情、新任务 | 用户重新发送新任务 |
| `AWAITING_CONFIRM` | 等待确认摘要 | 打开可信确认、拒绝、停止 | 用户响应或超时 |
| `BLOCKED` | 需要处理的原因 | 按原因核对结果、设置或停止 | 用户提交处置、完成设置或停止 |
| `COMPLETED` | 结果和证据摘要 | 详情、收起 | 自动收起或用户关闭 |
| `FAILED` | 失败步骤和影响摘要 | 重试、详情、停止 | 用户选择 |

同一时刻只能有一个用户权威状态。跨进程事件只是输入，body 内的 UI 状态机负责去重、排序和合法状态迁移。

## 7. UI 事件的 UX 最低契约

本节只规定 UI 正确显示所需的语义，不规定 RPC 名称或模块实现。

每个任务事件至少需要：

| 字段 | 要求 |
|---|---|
| `sourceSessionId` | 标识 brain 启动会话；重启后必须变化，用于安全重建 seq 水位 |
| `taskId` | 区分任务，旧任务事件不得覆盖当前任务 |
| `commandId` | UI 输入到 `prompt_start` 的受理关联；非输入事件可空，同一值只能创建一个任务 |
| `eventId` 或 `seq` | 在同一 `sourceSessionId` 内单调、有序、可去重 |
| `actionId` | 动作、暂停、停止和未知副作用处置可空但一旦涉及具体动作必须填写 |
| `state` | 来自有限枚举，不接收任意字符串驱动布局 |
| `stepIndex` | 已发生步骤序号，可空；不能冒充总进度 |
| `displayText` | 已脱敏、用户可读、长度受限 |
| `timestamp` | 支持最近步骤排序和断连诊断 |
| `requiresUser` | 区分纯展示、普通控制、可信确认和人工接管 |
| `resultKind` | 至少区分 `success`、`failed`、`paused`、`stopped`、`unknown_side_effect`；禁止仅用 `aborted` 让 UI 猜测 |
| `resolution` | 仅处理未知副作用时填写 `applied/not_applied/still_unknown`，并与原 `actionId` 绑定 |

禁止事项：

- 不允许用开放的 `payload` 字段覆盖 `kind/state/step` 等权威字段。
- 不允许 UI 直接渲染模型原文、工具参数、坐标、截图 OCR 全文或异常堆栈。
- 不允许把 EventBus 的普通展示事件当作敏感授权凭据。
- 不允许用“发送成功”代替“本地已受理”，也不允许用“模型回答结束”代替“任务完成”。
- 暂停/停止请求与 brain 的 run 结束事件必须可关联；`PAUSING`/`STOPPING` 不能只靠本地定时器伪造完成。
- `state`、`requiresUser`、`resultKind` 使用有限枚举；未知枚举进入 `FAILED`/`OFFLINE` 安全兜底并记录诊断，不得按默认 `RUNNING` 处理。
- 状态映射固定为：`paused -> PAUSED`、`stopped -> STOPPED`、`unknown_side_effect -> BLOCKED`；`STOPPED` 不得承载尚未核对的未知副作用。

文字输入发生在 `taskId` 创建之前时，输入事件必须先生成唯一 `commandId`；brain 接受后在 `prompt_start` 中回带该 `commandId` 并分配 `taskId`。同一 `commandId` 只能映射一个任务。

当前 `BrainEvent` 已进入 `contract.json` 唯一真源，但 `state/requiresUser/resultKind` 在 TypeScript、Kotlin 和 RPC 入站仍是开放字符串；实现负责人需补有限枚举与入站语义校验，不能把“字段齐全”视为契约已经封闭。

## 8. 后台运行边界

- 用户明确开启后台运行后，应用维持前台服务和常驻通知；用户关闭后不得自行恢复。
- 进程被系统回收时可以尝试恢复，但必须把任务状态标为“恢复中/需要确认”，不得盲目重放上一个动作。
- 手机重启后的自动恢复只能作为显式用户选项，并受系统/OEM 自启动权限约束；默认不偷偷开启。
- 无障碍在系统设置中仍启用但服务被 OEM 解绑时，可以尝试有限自愈；用户主动关闭无障碍时不得强行打开。
- 看门狗只做健康检查、有限重连和用户通知，不承诺绕过 Android 后台限制。

| UX-14 | 长文本与小屏 | 320dp 宽屏不溢出；当前一步最多两行，超长内容省略且可在详情查看 |

### 10.1 通用测试准备与证据规则

- 每条用例使用全新 `taskId`；设备开启屏幕录制，记录用例 ID、设备型号、Android 版本、应用版本和开始时间。
- 证据文件统一命名为 `UX-XX-screen.mp4`、`UX-XX-before.png`、`UX-XX-after.png`、`UX-XX-log.txt`；界面验收的 before/after 截图必须能看到 HUD 与目标应用的相对位置。UX-10 的原始感知截图是例外，它必须不含任何 HUD，并与同一时刻的 before/after 界面截图配对。
- 日志至少保留 body UI 状态、BrainEvent 的 `taskId/seq/state/stepIndex/resultKind`、动作 gate 开关和前台包名；以时间戳关联录屏，不以模型原文作为通过证据。
- 涉及付款、转账、真实验证码或真实账号的场景一律使用沙盒/假数据；出现真实副作用即判失败并停止测试。
- “不超过 300ms/10 秒”等时限以录屏帧时间或同一时钟的日志时间戳判定；无法证明时限即判“证据不足”，不能默认为通过。

### 10.2 UX-01 至 UX-14 可执行用例

#### UX-01 首次启动与授权

- 前置：全新安装，撤销悬浮窗、无障碍、通知权限；麦克风保持未授权。
- 步骤：打开应用；按引导逐项点击；在每个系统页面选择拒绝并返回；再次仅授予一项，重复检查，最后授予全部必需权限。
- 证据：录屏显示缺失项逐项变化；截图保存拒绝后的安全状态和全部就绪页；日志显示权限重新检查结果。
- 失败：崩溃、假显示“已就绪”、拒绝后自动重试弹窗、UI-0 主动索取麦克风或代替用户打开系统开关。

#### UX-02 文字指令入队

- 前置：必需权限已授予，brain 可连接，目标 App 位于可操作页面。
- 步骤：点控制球；点键盘入口；输入含唯一标记的短句；快速连续点发送两次；等待受理反馈。
- 证据：录屏统计从控制球到发送不超过三次明确操作，并在 300ms 内出现 `已收到 · 正在理解`；`text_input` 生成一个唯一 `commandId`，恰有一个 `prompt_start` 回带该 `commandId` 并映射到一个新 `taskId`。
- 失败：发送按钮重复入队、输入 Activity 抢占执行态、空文本建任务、显示“完成”而没有 brain 事件。

#### UX-03 执行可见性

- 前置：准备至少 3 个可观察动作且总步数未知的确定性任务。
- 步骤：发送任务；在规划、每个动作前后和完成时分别截图；打开详情前保持默认 HUD。
- 证据：录屏中默认只出现真实状态和当前一步；事件日志的 `stepIndex` 单调；截图和日志中没有坐标、JSON、思维链或伪造百分比。
- 失败：显示 `3/10`、固定进度条、模型原文、工具名、旧任务步骤覆盖当前任务或状态倒退。

#### UX-04 HUD 不挡操作

- 前置：选择含顶部、底部、全屏按钮的测试 App；记录控制球停靠位置。
- 步骤：分别让 agent 操作三个区域；用户在状态条存在时手动滚动/点击目标 App；观察前台包和焦点。
- 证据：录屏覆盖三个区域，动作结果与无 HUD 对照一致；日志记录目标 App 仍为前台；状态条触摸事件数为零。
- 失败：HUD 拦截目标点击、用户 App 失焦、状态条可点击、控制球覆盖目标且无法拖离。

#### UX-05 运行中查看步骤

- 前置：运行一个包含长等待或可控停顿的任务，至少已经完成 3 步。
- 步骤：运行中点控制球；记录 `正在暂停…`；等待面板出现；面板打开期间持续观察目标 App 和动作日志。
- 证据：录屏顺序必须是 `RUNNING -> PAUSING -> PAUSED/BLOCKED -> 面板`；面板出现后无新动作事件；展示最近 3 至 5 条已发生步骤。
- 失败：先开面板再暂停、面板期间仍点击设备、直接跳 `PAUSED` 但在途结果未知、历史步骤包含未完成动作。

#### UX-06 继续执行

- 前置：UX-05 已进入 `PAUSED`，上一个动作结果可验证成功。
- 步骤：点继续；观察面板关闭；等待重新感知；让任务执行下一步。
- 证据：录屏显示 `面板关闭 -> 正在确认当前界面… -> THINKING/RUNNING`；日志显示新的感知事件和更高步骤号，上一动作没有重复调用。
- 失败：面板仍遮挡目标、直接恢复旧计划、重复上一个成功动作、关闭后没有当前状态反馈。

#### UX-07 停止与未知副作用

- 前置：分别准备规划中、单个手势在途、复合 `skill.run` 三个停点；禁止真实支付。
- 步骤：在每个停点点击停止；快速重复点击；等待 brain settle；对未知结果分别提交 `applied/not_applied/still_unknown`；检查控制球、通知和任务列表。
- 证据：日志显示 action gate 先关闭、pi run 随后 abort；停止后无新动作；可验证时为 `STOPPED/已停止`，不可验证时为 `STOPPING -> BLOCKED/停止后需要你检查`；核对事件绑定原 `actionId`，核对完成后只进入 `STOPPED` 而不恢复任务。
- 失败：停止后开始新动作、自动重试/继续、把 `aborted` 直接渲染为成功停止、重复停止生成多个任务。

#### UX-08 敏感确认

- 前置：body 生成一次性 nonce 的沙盒敏感动作，确认文案中不含真实密钥。
- 步骤：核对文案和目标；分别用批准、拒绝、返回、关闭、超时完成五次；重复使用同一 nonce。
- 证据：录屏显示可信确认表面和完整上下文；日志显示批准只消费一次 nonce，其他路径均为拒绝且无动作调用。
- 失败：关闭等价批准、文案来自模型自由文本、nonce 可重放、确认后目标/参数改变。

#### UX-09 支付红线

- 前置：仅使用支付沙盒或停在最终提交前的模拟页面。
- 步骤：发送“付款/转账”类指令；观察 agent 到达红线；用户尝试从悬浮层继续或寻找自动付款按钮。
- 证据：录屏显示 `需要你接管`，agent 不再发出提交动作；日志无支付工具调用；面板只提供用户接管、查看和停止。
- 失败：悬浮层提供自动付款、agent 自动提交、用“已完成”代替用户接管结果。

#### UX-10 截图与恢复

- 前置：分别准备 `RUNNING`（状态条+控制球）和 `PAUSED/BLOCKED`（面板+控制球）两个合法状态；仅在测试桩中允许暂停态触发只读截图。
- 步骤：两个状态各触发一次截图/视觉感知；保存原始截图；等待感知完成；再次查看当前 HUD。
- 证据：两张原始感知截图的像素检查均不含状态条、球或面板，并分别配有显示 HUD 相对位置的 before/after 截图；日志有 `OverlayGate.hide` 和恢复事件；每次恢复后按截图前权威状态恢复对应表面。
- 失败：截图含半透明 HUD、恢复只剩控制球、恢复错误状态或遮挡目标应用。

#### UX-11 brain 断连

- 前置：任务运行中，准备可控的 brain 进程停止/IPC 断开方法。
- 步骤：断开 brain；等待 10 秒；尝试点击控制球和停止；恢复 brain 后观察重连。
- 证据：录屏和日志显示 10 秒内进入 `OFFLINE/连接中断`，action gate 关闭，提供停止和重试；恢复后先感知而非重放。
- 失败：无限转圈、继续发设备动作、自动重放最后一步、没有用户可见诊断入口。

#### UX-12 进程恢复

- 前置：在已完成一个副作用动作、下一步尚未执行的任务点主动杀掉 brain/body 进程。
- 步骤：重启应用服务；观察恢复态；检查前台界面；选择继续或停止。
- 证据：日志显示旧任务进入恢复/待确认，重新感知后才允许新动作；无法确认时为 `BLOCKED` 并要求人工处理。
- 失败：按旧队列盲重放、跳过感知直接点击、恢复后 taskId/步骤错配。

#### UX-13 OEM 后台限制

- 前置：在目标 OEM 上关闭自启动/后台活动或用系统回收模拟；用户未授权绕过设置。
- 步骤：开启后台运行；将应用置后台并触发系统限制；等待恢复或通知；按引导进入设置后返回。
- 证据：录屏显示诚实的 `连接中断/需要设置` 和一次性引导；日志无高频拉活循环；恢复后状态可验证。
- 失败：宣称永久在线、循环弹窗、偷偷重新开启用户关闭的开关或恢复未知动作。

#### UX-14 长文本与小屏

- 前置：320dp 宽度、横竖屏各一台/一组模拟器；准备中英文混合长指令和极长当前步骤。
- 步骤：输入、规划、运行、暂停、错误和完成各状态；旋转屏幕并打开最近步骤和详情。
- 证据：截图无裁切/重叠/横向滚动；当前一步最多两行并有详情入口；录屏显示按钮和文字始终在容器内。
- 失败：文字溢出、按钮被挤出屏幕、状态变化导致控制球跳动、长文本遮挡停止/继续。

M6 交互绿出口统一改为：**真机不接 PC，从侧边控制球输入文字指令，观察真实当前步骤，安全暂停查看历史，再继续或停止；HITL 和结果均有可理解反馈，整个过程不遮挡或误触目标应用。**

## 10A · UI-1 语音行为基线草案（U3，未冻结）

> 本节是 UI-1 预研草案，不改变 UI-0 的文字首版范围。ASR 负责把声音变成待确认文本，pi-agent-core 仍是唯一大脑；Kestrel 的 ASR/Activity 行为只复用交互经验，不复用其编排核心。

### 10A.1 输入方式与生命周期

- 移动端默认采用**按住说话、松开发送前预览**：用户按住语音按钮时立即进入 `LISTENING`，松开后停止录音并显示识别文本；不默认持续监听，不默认 KWS。
- 控制球长按可直接进入语音输入；待命面板的语音按钮进入同一输入组件。长按控制球的行为不能与运行中“暂停”点击冲突：运行任务中长按只打开控制面板，不开始录音。
- 按下时先更新本地 UI，再并行准备 ASR；首次加载慢不能吞掉用户已经说出的前半句。松开、取消、系统打断和超时都必须关闭录音资源。
- 识别结果先进入可编辑预览框，用户点击发送后才生成任务。ASR 文本不得绕过预览直接调用 pi 或 body，尤其不能直接执行敏感动作。
- 预览框提供重录、编辑、发送、取消；空文本、纯噪声或低置信结果只提示“没有听清，请再说一次”，不创建任务。
- 当前一次性 `speech.asr` RPC 只能按静音/超时结束，不能直接满足按下/松开的生命周期；UI-1 实现需补可取消的 start/stop 会话或明确降级为“点击开始、再次点击结束”，不得让文案和实际录音方式不一致。

### 10A.2 权限、音频焦点与错误

| 场景 | 用户可见行为 | 安全要求 |
|---|---|---|
| 首次使用 | 用户按下语音按钮后才申请麦克风；授权返回后仍需再次按下才录音 | 不在启动时索取，不因授权自动录音 |
| 拒绝/永久拒绝 | 显示用途和系统设置入口，保留文字输入 | 不循环弹窗、不伪装成 brain 故障 |
| 无声/超时/ASR 无模型 | 预览区显示可重试原因，保留编辑和文字入口 | 不把空结果发送给 pi |
| 来电、其他 App 占用音频 | 立即结束录音并提示可重试 | 释放 AudioRecord/焦点，不执行半句指令 |
| 应用退后台或 overlay 被系统移除 | 录音取消，任务不入队 | 不在后台偷偷继续录音 |
| ASR 网络/IPC 断开 | 显示“语音服务不可用”，可改用文字 | 只重试识别，不重试设备动作 |

### 10A.3 TTS 关键节点文案与打断

- 默认不逐步播报，不朗读用户原话、识别全文、验证码、金额、账号、联系人、通知正文或截图 OCR；敏感文本只在可信屏幕显示。
- 可选播报节点及固定短文案：
  - 受理：`已收到，正在理解`（默认以短提示音/视觉反馈为主，避免每条任务打断环境）。
  - 需要确认：`需要你确认后才能继续`。
  - 需要接管：`这一步需要你处理，处理好后点继续`。
  - 完成：`任务已完成`。
  - 失败：`任务未完成，已停止自动操作`。
  - 断连/未知副作用：`连接中断，已停止操作，请检查当前界面`。
- 用户点击控制球、开始新的录音或按停止时，先调用 `speech.interrupt`/停止 TTS，再处理新输入；不能让 TTS 与 ASR 互相录入。
- TTS 失败不改变 brain/body 状态；视觉文字反馈必须独立可用。系统音频焦点丢失时停止播报并释放资源。

### 10A.4 状态色点和非颜色语义

状态点只作低注意力提示，不能承载唯一语义；每个颜色都必须同时有图标、文字和可访问性描述：

| 状态 | 颜色语义 | 动效/文字 |
|---|---|---|
| `IDLE/MINI` | 中性灰 | 静止点，`待命` |
| `LISTENING` | 蓝绿色 | 轻微呼吸，麦克风图标，`正在听` |
| `THINKING` | 蓝色 | 慢速脉冲，`正在理解` |
| `RUNNING` | 绿色 | 稳定点，`执行中 · 当前一步` |
| `PAUSING/STOPPING` | 琥珀色 | 单次收缩，`正在暂停/停止中` |
| `PAUSED/BLOCKED/AWAITING_CONFIRM` | 橙色 | 静止提示，配暂停/警示/确认图标和行动文案 |
| `COMPLETED` | 绿色 | 一次短闪后回到待命 |
| `FAILED/OFFLINE` | 红色 | 不闪烁，明确错误/断连图标和恢复入口 |

动效不得持续吸引注意或改变控制球触摸区；状态转换必须可由录屏和无障碍树判定。

### 10A.5 UI-1 预研验收入口

UI-1 冻结前至少补齐以下五条真机用例，证据沿用 §10.1 的录屏、截图和事件日志规则：

| ID | 操作 | 判定证据 |
|---|---|---|
| `UI1-V01` | 按住说话、松开、上滑取消各一次 | 录屏与音频会话日志证明按下即 `LISTENING`、松开即停止、取消不生成 `commandId` |
| `UI1-V02` | 首次拒绝、永久拒绝、从设置返回后重试 | 只在点击语音时申请；拒绝不循环弹窗；授权返回不自动录音；文字入口始终可用 |
| `UI1-V03` | 识别出可执行指令后先编辑再发送，并做一次取消 | 发送前无 `prompt_start`/设备动作；发送文本等于编辑后内容；取消不建任务 |

## 11. 对现有架构草案的审计差异

以下内容需要实现负责人同步修订 `docs/05/06/10` 并在后续实现走查中关闭：

1. “展开卡片内直接放输入框，输入时临时切换 overlay focus”改为独立半透明输入 Activity。
2. “执行态步骤流半透滚动”改为默认只显示当前一步；最近 3 至 5 步只在安全暂停后展示。
3. “一个悬浮窗在展示和交互间切换”改为不可触摸状态条与可触摸侧边控制球两个独立表面。
4. `brain.event(kind/text/step/payload)` 必须改成受契约约束、与 `taskId/seq` 绑定的类型化事件，不能直接扁平化开放 payload。
5. G5 的“步骤流全程可见”改为“当前一步全程可见、历史步骤按需可见”。
6. UI-0 验收不得依赖通知栏完成日常暂停/停止；通知只作为无 overlay 或系统限制下的兜底。
7. 暂停/停止不能复用 Kestrel 的本地 orchestrator 控制，也不能只设置 brain stop flag；必须是 body task action gate 先关闭，再让 pi run abort/settle，最后重新感知。
8. pi-agent-core 的设备副作用工具必须显式串行化并传递/响应 abort signal；已经下发 body 的动作按“不可回滚、结果可能未知”处理。
9. `finish(aborted)` 不能同时表示暂停和停止；状态与结果契约需区分 `paused/stopped/unknown_side_effect`。
10. `BrainEvent` 需加入 brain 启动会话身份和动作关联字段；不能以跨进程全局单调 seq 为前提，也不能让进程重启后的低 seq 永久被旧水位丢弃。
11. UI-1 不得把模型完整回复直接送入 `speech.say`；只能发送固定、脱敏的关键节点文案，TTS 异常不得把已完成或执行中的任务改成 crashed。

在这些差异关闭前，`BD-10/CT-06/BR-10` 应保持“设计中”，不能标记为已实现。
