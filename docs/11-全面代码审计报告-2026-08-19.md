## 1. 执行摘要

当前版本具备完整的 brain/body 双进程骨架，brain 侧守卫、证据核验、契约镜像和本地模型降级链已有较好的工程基础。但 body 侧多个动作入口没有共享同一套授权策略，敏感会话状态也没有绑定真实前台窗口，因此“支付红线/敏感操作不可绕过”的架构承诺尚未成立。

本次确认：

| 级别 | 数量 | 结论 |

| P0 | 5 | 不建议以当前版本宣称安全闭环完成；应先修复并补真实 body/真机验证 |

| P2 | 2 组 | 资源释放、配额和测试覆盖不足 |

## 2. P0 问题

### P0-01 敏感会话状态没有绑定真实前台应用

- **位置**：[SensitiveSession.kt](../body/core/src/main/kotlin/com/superagent/body/core/security/SensitiveSession.kt:22)、[BodyCore.kt](../body/core/src/main/kotlin/com/superagent/body/core/BodyCore.kt:166)
- **问题**：`SensitiveSessionTracker` 只在 `control.launch` 和 `control.home` 中更新。用户直接从系统或其他应用打开银行/聊天应用时，状态仍是默认的非敏感；`home/launch` 还在动作结果返回前就清除或切换状态。
- **影响**：敏感应用内的 `selectOption` 可能不触发二次确认；一次失败的后台启动也可能让原敏感前台窗口失去保护。
- **修复方向**：每次受控动作前读取 `rootInActiveWindow.packageName`，以实际前台包名计算敏感态；只有观察到真实前台切换后才更新会话和清理批准状态。

### P0-02 坐标动作绕过敏感会话二次确认

- **位置**：[BodyCore.kt](../body/core/src/main/kotlin/com/superagent/body/core/BodyCore.kt:102)
- **问题**：`control.tap` 和 `control.longPress` 只调用 `commitBoundaryAt`，没有调用 `SensitiveSessionTracker.needsExtraConfirm`。该检查仅存在于基于文字的 `selectOption/selectSpec` 路径。
- **影响**：在敏感聊天、银行或支付会话内，模型可以改用坐标点击“发送”“删除”“转账”等敏感动作，绕过二次确认。
- **修复方向**：所有动作入口统一进入节点感知的授权服务；坐标命中的节点既要做提交边界判定，也要做敏感会话动作判定。

### P0-03 坐标提交边界校验可被重叠节点绕过

- **位置**：[BodyCore.kt](../body/core/src/main/kotlin/com/superagent/body/core/BodyCore.kt:354)、[ScreenPerceiver.kt](../body/core/src/main/kotlin/com/superagent/body/core/perception/ScreenPerceiver.kt:87)
- **问题**：`commitBoundaryAt` 使用 `firstOrNull`，只检查第一个包含点击坐标的节点。无障碍树按父节点到子节点遍历，普通文案的父容器可能先命中，内部“提交订单/立即支付”子节点不会再检查。
- **影响**：支付或提交按钮可能因父子节点边界重叠而放行，直接破坏坐标绕行防线。
- **修复方向**：检查全部相交节点；优先选择最深、可点击、面积最小的节点，同时只要任一命中节点是提交边界就拒绝。需要用重叠父子节点的真实 UI 树补真机测试。

### P0-04 技能回放直接调用 Controller，绕过 body 安全闸门

- **位置**：[SkillStore.kt](../body/core/src/main/kotlin/com/superagent/body/core/skills/SkillStore.kt:81)、[SkillStore.kt](../body/core/src/main/kotlin/com/superagent/body/core/skills/SkillStore.kt:191)
- **问题**：`skill.run` 的 `executeStep` 直接调用 `Controller`，没有复用 RPC 的坐标提交检查、敏感会话检查、前台状态重算或统一 HITL 授权。`skill.learn` 也接受调用方提供的轨迹，只过滤工具名和 `located`。
- **影响**：已固化技能或被构造的 trace 可以执行本应被 body 拦截的坐标点击、文本输入和应用启动；安全控制被分成两套且回放路径更弱。
- **修复方向**：建立唯一的 `ActionAuthorization/ActionExecutor`，RPC 和 replay 只能通过该服务执行；学习时校验 trace 来源、当前前台应用、提交边界和敏感动作，不接受未经 body 证明的任意轨迹。

### P0-05 HITL 批准不绑定原动作且不是单次消费

- **位置**：[BodyCore.kt](../body/core/src/main/kotlin/com/superagent/body/core/BodyCore.kt:320)、[SensitiveSession.kt](../body/core/src/main/kotlin/com/superagent/body/core/security/SensitiveSession.kt:49)
- **问题**：`hitl.confirm` 接受调用方自定义的 `prompt` 和 `action`，服务端没有记录“此前被拒绝的具体动作”并进行匹配。批准后 `isApproved` 只检查两分钟 TTL，不会消费批准。
- **影响**：模型可以展示与实际动作无关的确认文案；一次用户批准可重复放行同标签的多个发送、删除或修改操作。
- **修复方向**：拒绝时由 body 生成一次性 nonce，绑定前台包名、动作标签、参数摘要和原始请求；通知展示服务端生成的规范化内容；批准成功后原子消费 nonce。

## 3. P1 问题

### P1-01 未经过 `task.finish` 仍会被记为成功

- **位置**：[main.ts](../brain/src/main.ts:194)、[main.ts](../brain/src/main.ts:238)、[runState.ts](../brain/src/runState.ts:97)
- **问题**：`finishVerified` 虽已加入状态模型，但 REPL、续跑和语音循环在 agent prompt 正常返回后仍无条件调用 `finishRun("success")`。
- **影响**：只要模型停止输出，即使没有证据核验、没有完成目标，也会被归档为成功并失去断点续跑资格。该行为与最新提交说明中的“finishVerified 区分口头收笔”不一致。
- **修复方向**：任务型输入必须要求 `finishVerified == true` 才能成功；未调用 `task.finish` 应落为 `needs_human`、`failed` 或可续跑的中断态。对话型输入需要单独的会话语义，不应复用任务成功态。

### P1-02 `/blob/{id}` 实际路由不可达

- **位置**：[BodyServer.kt](../body/core/src/main/kotlin/com/superagent/body/core/http/BodyServer.kt:67)、[client.ts](../brain/src/ipc/client.ts:110)
- **问题**：GET 路由先将完整 URI 规范化为 `blob/<id>`，但 `when` 分支只匹配精确字符串 `"blob"`。客户端请求的是 `/blob/${ref}`，因此会落入 `NOT_FOUND`。
- **影响**：真实视觉链路无法从 body 取回截图，brain 的 VLM marks 只能在 mock body 中通过。
- **修复方向**：显式解析 `blob/<id>` 路径，限制为单个安全文件名，并增加真实 `BodyServer` 路由测试。

### P1-03 RPC 幂等和超时不能保证重试安全

- **位置**：[BodyServer.kt](../body/core/src/main/kotlin/com/superagent/body/core/http/BodyServer.kt:119)、[BodyServer.kt](../body/core/src/main/kotlin/com/superagent/body/core/http/BodyServer.kt:136)
- **问题**：幂等缓存只在 handler 完成后写入；同一 key 的并发请求可以同时进入 handler。超时只返回 `TIMEOUT`，后台 `GlobalScope` 协程仍继续执行且没有取消或状态跟踪。
- **影响**：网络重试可能重复手势、重复输入或重复启动应用；调用方收到失败时，设备动作可能仍在进行。
- **修复方向**：先原子预留 in-flight key，并让并发请求共享同一个结果；使用结构化 Job；不可取消的动作超时必须标记为 `unknown`，禁止客户端按失败自动重试。

### P1-04 RPC 请求体没有大小上限

- **位置**：[BodyServer.kt](../body/core/src/main/kotlin/com/superagent/body/core/http/BodyServer.kt:153)
- **问题**：`readBody` 信任 `Content-Length` 并直接分配 `ByteArray(length)`，没有拒绝超大、负数、缺失或分块输入，也没有连接并发配额。
- **影响**：持有 bearer token 的客户端可触发内存耗尽；该风险会放大 token 泄漏后的影响。
- **修复方向**：设置小而明确的请求上限，先校验长度再分段读取；限制并发连接和单方法队列深度。

### P1-05 技能选择器可能报告虚假成功，回放签名口径不一致

- **位置**：[OptionSelector.kt](../body/core/src/main/kotlin/com/superagent/body/core/control/OptionSelector.kt:50)、[SkillStore.kt](../body/core/src/main/kotlin/com/superagent/body/core/skills/SkillStore.kt:136)
- **问题**：selector 忽略 `controller.tap` 的 `ActionResult`，手势取消时仍可能返回 `located=true`。同时 selector 保存的是目标节点签名，而回放校验的是整屏稳定签名。
- **影响**：错误轨迹可能被固化；合法的多步技能又会在后续步骤稳定地误判 `stale`，造成状态机和回放结果失真。
- **修复方向**：只在手势成功且后置条件通过后返回成功；所有动作统一保存“动作完成后的整屏稳定签名”，学习和回放使用同一签名函数。

### P1-06 视觉数据和 RPC 传输的隐私边界不足

- **位置**：[ScreenshotService.kt](../body/core/src/main/kotlin/com/superagent/body/core/screenshot/ScreenshotService.kt:108)、[BodyContext.kt](../body/core/src/main/kotlin/com/superagent/body/core/BodyContext.kt:19)、[AndroidManifest.xml](../body/app/src/main/AndroidManifest.xml:25)
- **问题**：截图先以原始 JPEG 写入 blob，再由 brain 取图送 VLM；body 侧没有敏感会话禁止、栅格脱敏或导出前复核。token 长期保存并跨 body 重启复用，服务绑定 `0.0.0.0` 且允许明文 HTTP。
- **影响**：敏感页面可能被持 token 的客户端读取并外送；局域网明文传输可暴露 bearer token，重启也不会使泄漏 token 失效。
- **修复方向**：敏感会话默认禁止视觉导出；持久化前完成可测试的 body 侧脱敏并设置 TTL；使用 boot-scoped session secret 或 bootId 绑定，逐步迁移到 Unix domain socket/受保护本地通道。

## 4. P2 问题与工程缺口

### P2-01 截图异常路径可能泄漏 Image 句柄

- **位置**：[ScreenshotService.kt](../body/core/src/main/kotlin/com/superagent/body/core/screenshot/ScreenshotService.kt:69)
- **问题**：`Image` 只在正常路径显式关闭；获取后在像素转换、Bitmap 或文件写入阶段异常时直接进入 catch，未必执行 `image.close()`。
- **影响**：连续异常可能耗尽 `ImageReader` 的两帧缓冲，之后截图永久无法获取。
- **修复方向**：对每个已获取 `Image` 使用 `try/finally` 或 `use`，并为 capture 失败路径增加重复故障测试。

### P2-02 多个认证入口没有配额，核心 body 缺少测试

- `speech.say` 每次请求创建独立线程；`skill.learn` 接受无上限 trace；HITL 挂起请求和技能文件没有明确数量、大小、磁盘和并发限制。
- `body/core` 没有真实测试源码。现有 brain smoke 使用 mock body，无法覆盖真实 `BodyServer` 路由、超时/幂等、技能回放、敏感状态、截图资源释放等路径。
- 建议新增 JVM 可测试的 policy/action/server seam，再补 Android instrumentation 和真机用例；不要只扩展 mock body。

## 6. 建议修复顺序

1. 先合并唯一 `ActionAuthorization`，覆盖 RPC、selector 和 skill replay；同时修复真实前台敏感态和重叠节点命中策略。
2. 重做 HITL 为动作绑定、前台绑定、单次消费的 body-side nonce，并补支付/发送/删除三类真机拒绝与批准用例。
3. 修正 `task.finish` 终态语义、blob 路由、selector 结果传播和回放签名口径。
4. 给 BodyServer 增加请求上限、in-flight 幂等、结构化取消和 body/core 集成测试。
5. 最后处理截图脱敏、token 生命周期、明文传输和语音/技能资源配额，再重新跑 P0 真机验收。

## 7. 审计判断

**当前版本：不建议合入“安全闭环完成”或宣告 P0 全绿。**

brain 侧的基础工程验证是绿色的，但它们主要证明 mock 交互和纯函数守卫正确，不能证明 Android body 的授权边界。至少在 P0-01 至 P0-05 修复并完成真实 body/真机验证前，支付红线、敏感会话和技能回放均应视为未闭合。
